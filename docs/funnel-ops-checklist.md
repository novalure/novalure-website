## Double opt-in system of record

Confirmed Playbook marketing consent is stored in Resend:

- Segment: `RESEND_CONTACT_SEGMENT_ID`
- Topic: `RESEND_MARKETING_TOPIC_ID` (default subscription must be `opt_out`)
- Contact properties: `doi_confirmed_at`, `doi_source`, `privacy_policy_version`, `requested_playbook`, `doi_token_fingerprint`

The email link opens a confirmation page. Only the POST generated by the confirmation button writes the opt-in, so automated link scanners cannot confirm consent through a GET request. Resend is the marketing-consent system of record. HubSpot remains the CRM lead destination; synchronizing HubSpot marketing-subscription status additionally requires a HubSpot private-app token and subscription type ID.

Confirmation links contain a v2 signed audience, token ID and accepted privacy-policy version. The audience is bound to Production or the immutable `VERCEL_URL` of one Preview deployment. Redis keys and Resend idempotency keys include the deployment namespace, so links, replay state and quotas cannot cross environments. Redis stores only a hash of the token ID and atomically transitions it through pending, processing and terminal used/blocked states. Resend stores the canonical token fingerprint as `doi_token_fingerprint`; the raw token is never stored. Existing global unsubscribes, explicit topic `opt_out` states and missing/ambiguous topic states are preserved. Signing-key rotation uses `DOUBLE_OPT_IN_PREVIOUS_SECRET` only while a current, at least 32-byte `DOUBLE_OPT_IN_SECRET` remains configured.

Resend contact creation uses a one-row asynchronous import with `on_conflict=skip`. Its import ID and created/skipped/failed terminal state are retained in deployment-scoped Redis for 48 hours. Nonterminal confirmation retries resume that exact import before reading contact preferences; they never start by evaluating a potentially partial contact.

## Playbook abuse protection

- Preview Vercel Firewall rate-limit ID: `novalure-playbook-submit-preview` (5 requests per 600 seconds, Preview condition, API-controlled key)
- Production Vercel Firewall rate-limit ID: `novalure-playbook-submit` (create only after Preview QA)
- Persistent recipient limit: 3 distinct submissions in an exact rolling 24-hour window
- A client-generated UUID remains stable across double-clicks/retries and is reused for the Redis member, signed token, HubSpot at-most-once marker and deployment-scoped Resend idempotency keys
- Redis keys contain only a SHA-256 digest of the normalized recipient address
- Vercel injects the canonical `KV_REST_API_URL` and `KV_REST_API_TOKEN` pair for the connected Upstash database; a complete direct `UPSTASH_REDIS_REST_*` pair is supported for local use
- The matching environment-specific code-instrumented Firewall rule must be published before a deployed Preview/Production API test
- Missing Firewall or Redis configuration in deployed Preview/Production fails closed with HTTP 503; the Firewall SDK intentionally bypasses an absent rule during local development

## Internal notifications and CRM tasks

- Resend email notification to `hello@novalure.eu` is implemented for audit requests.
- Playbook requests are submitted to HubSpot using the configured form GUID. A HubSpot failure is logged and no longer blocks Playbook delivery.
- HubSpot submissions use an atomic Upstash claim/complete/release state machine: concurrent duplicates are serialized, acknowledged submissions are suppressed for 30 days, failed attempts reopen for retry, and a changed payload using the same submission ID is rejected with HTTP 409.
- Because HubSpot Forms has no provider-side idempotency key, an ambiguous transport failure can duplicate a form event on retry. Reconcile such events using the stable submission ID included in the owner notification.
- Follow-up CRM task creation is not confirmed because no HubSpot private app token or task endpoint is configured.
- No-show reminder workflow is not confirmed because calendar workflow configuration is outside this repository.
